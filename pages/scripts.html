QUICK REFERENCE

Example safe checks

These small snippets demonstrate read-only checks. They are examples for reference, not a substitute for reviewing the full script, permissions, and target environment.

Read-only examples

Linux · Wazuh agent status

Bash
agent-status.sh
#!/usr/bin/env bash
# Read-only service status check
if command -v systemctl >/dev/null 2>&1; then
    systemctl is-active wazuh-agent
    systemctl --no-pager --full status wazuh-agent
else
    echo "systemctl is not available on this host."
fi

Run on a Linux endpoint where systemd and the Wazuh agent package are installed. The command reports service state; it does not start, stop, or restart the service.

Windows · Wazuh agent status

PowerShell
agent-status.ps1
# Read-only service status check
$service = Get-Service -Name "WazuhSvc" `
    -ErrorAction SilentlyContinue

if ($null -ne $service) {
    $service |
        Select-Object Name, DisplayName, Status
} else {
    Write-Output "Wazuh agent service not found."
}

Run in PowerShell on the Windows endpoint. Service naming can vary by package/version; confirm the installed service name if this example returns no result.

EXECUTION CHECKLIST

Before running any script

Use a controlled workflow so that script output is reproducible, attributable, and safe for your lab.

StepWhat to verifyWhy it matters
01 · ScopeConfirm the script target is your own lab VM or an explicitly authorized system.Prevents unintended activity on systems outside the lab.
02 · InspectRead the entire script and identify commands that write files, change services, or require elevated permissions.Understand side effects before execution.
03 · TestUse a snapshot or test VM first; record OS and script version.Supports recovery and reproducible results.
04 · CaptureSave output, execution time, host name, and relevant screenshots without exposing credentials or secrets.Provides useful evidence for reports and troubleshooting.
05 · ReviewCompare the output with Wazuh agent status, alerts, and the relevant logs.Corroborates script output with telemetry rather than assuming success.
SCRIPT WORKFLOW

From script to documented result

A repeatable process for building a credible SOC portfolio entry.

01

Define the task

Write down the operational problem, target host, expected output, and whether the script is read-only or makes changes.

02

Develop & review

Keep scripts small, readable, commented, and free of hard-coded passwords, tokens, or private information.

03

Test in the lab

Run against a disposable or snapshotted VM, check exit status, and compare the output with system and Wazuh records.

04

Record evidence

Document prerequisites, usage, sample sanitized output, limitations, and links to related investigation notes.

Repository and safety note

The catalog links point to the planned paths under content/scripts/. Those files must be created in your repository before the links will open. Review each script before running it, use it only on systems you own or are authorized to administer, and never commit passwords, API keys, tokens, private IP details you do not want public, or unredacted security logs to a public repository.
